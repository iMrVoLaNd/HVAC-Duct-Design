# ТЗ: порт MEP Parameter Sync з pyRevit/IronPython на C#

## 1. Мета

Створити C#-застосунок для Revit, який відтворює поточну поведінку команди **MEP Parameter Sync** з розширення `HVAC_Design.extension` без зміни бізнес-правил.

Застосунок повинен:

- формувати значення спільного параметра `ADSK_Система_Имя` на MEP-елементах;
- формувати окреме значення `Unicode Сортування` для порядку систем у специфікаціях;
- працювати у двох режимах: ручний запуск і Dynamic Updater;
- застосовувати ті самі правила назв, пріоритети, виключення та граничні випадки, що й поточний Python-модуль;
- зберігати налаштування у JSON і дозволяти редагувати їх у UI;
- не змінювати елементи в режимі аудиту.

Результат: Revit add-in на C#, функціонально сумісний з поточним інструментом. Для однакових моделі, конфігурації та вхідних даних результат у `ADSK_Система_Имя` і `Unicode Сортування` має збігатися з Python-версією.

## 4. Дані та параметри

### 4.1. Вхідні дані елемента

Для кожного елемента читати:

1. `BuiltInParameter.RBS_SYSTEM_NAME_PARAM` — вихідне ім'я системи.
2. Тип системи:
   - `RBS_DUCT_SYSTEM_TYPE_PARAM` для повітроводів;
   - `RBS_PIPING_SYSTEM_TYPE_PARAM` для труб;
   - системний тип, отриманий із відповідного параметра/елемента типу для інших MEP-елементів.
3. Категорію, ім'я сімейства, тип, статус вкладеності.

Для ізоляції та облицювання джерелом імені та типу є **елемент-власник**, а не власний параметр ізоляції. Це обов'язкове правило сумісності.

### 4.2. Цільові параметри за замовчуванням

| Призначення | Поточне значення |
|---|---|
| Параметр імені | Shared Parameter `ADSK_Система_Имя` |
| GUID параметра імені | `24c33696-0fa2-4a85-affd-e47d1cf20fb3` |
| Параметр сортування | Project Parameter `Unicode Сортування` |
| Режим сортування | Увімкнений |

Ідентифікувати Shared Parameter перш за все за GUID. Project Parameter ідентифікувати за налаштованим ключем/іменем. Якщо цільовий параметр не знайдено, не виконувати запис і показати діагностику.

## 5. Конфігурація

Файл `settings.json` має UTF-8 кодування та три верхні секції:

```json
{
  "settings": { },
  "system types": { },
  "equipment": [ ]
}
```

### 5.1. `settings`

Має зберігати щонайменше:

- `config_version`: поточна версія — `3`;
- джерело, ім'я, ключ і GUID параметра імені;
- `sort_mode`, джерело, ім'я/ключ/GUID параметра сортування;
- `sort_system_order` і `default_sort_system_order`;
- `universal_markers`;
- `exclude_family_prefixes`;
- `audit_mode`;
- налаштування логування: `enable_logging`, каталог, ліміт днів, ліміт розміру;
- `ui_theme`, `enable_perf_metrics`.

### 5.2. Правило типу системи

Ключ словника `system types` — **точна назва типу системи Revit**. Значення:

```json
{
  "strategy": "DynamicNameStrategy",
  "prefix": "П",
  "log": "Припливна система"
}
```

Допустимі стратегії:

- `DynamicNameStrategy`;
- `ConstantNameStrategy`;
- `TransitNameStrategy`;
- `ClearNameStrategy` — підтримати у ядрі, але заборонити в користувацьких правилах конфігурації, як у поточній версії.

Для `DynamicNameStrategy` і `ConstantNameStrategy` `prefix` обов'язковий. Для кожного правила `log` обов'язковий.

### 5.3. Правило обладнання

```json
{
  "search": ["Х3", "Х4"],
  "exclude": ["ПК", "РК"],
  "prefix": "К",
  "sort_prefix": "К",
  "strategy": "DynamicNameStrategy",
  "log": "Блок системи кондиціонування",
  "system_type_key": ""
}
```

- `search`: рядок або масив, обов'язково непорожній.
- `exclude`: рядок або масив, необов'язковий.
- Масив правил має порядок. Перше правило, що збіглося і не виключене, перемагає.
- `system_type_key` використовується для сортування; якщо порожній, застосувати спеціальний ключ `Кілька типів систем`.

## 6. Модель формування імені

### 6.1. Загальний алгоритм

```text
отримати системне ім'я
якщо ім'я порожнє -> результат "", стратегія Clear
видалити Unicode format characters (категорія Cf)
якщо MechanicalEquipment -> застосувати правила обладнання
інакше знайти точне правило за назвою типу системи
якщо правила немає -> передати нормалізоване ім'я без змін
застосувати стратегію правила
```

`Transit` означає, що початкове ім'я вже є результатом. Нормалізація символів категорії `Cf` виконується до будь-якого аналізу.

### 6.2. DynamicNameStrategy

Результат дорівнює `prefix + extractedNumber`.

Алгоритм `extractedNumber` має бути ідентичним Python-версії:

1. Знайти маркер у тексті:
   - спершу `prefix` правила;
   - потім маркери з `universal_markers`.
2. Порівняння маркерів case-insensitive.
3. Маркер має бути окремим токеном: зліва та справа не може бути літери або цифри. Якщо маркер стоїть на початку, це також допустимо.
4. Видалити лише перше знайдене входження маркера.
5. Якщо текст містить кому, для розбору взяти частину до першої коми.
6. Якщо в робочому тексті є одна або більше крапок, взяти сегмент після першої крапки.
7. Взяти перший збіг регулярного виразу: цифри `\d+` і необов'язковий суфікс: `-літери`, `-цифри` або літери.
8. Якщо числа не знайдено, **не вигадувати ім'я**: повернути нормалізоване вихідне ім'я зі стратегією `TransitNameStrategy` і статусом «немає правила/номера».

Приклади очікуваного принципу:

| Початкова назва | Префікс правила | Результат |
|---|---:|---|
| `П1` | `П` | `П1` |
| `П.12` | `П` | `П12` |
| `Х3.7, В1` | `К` | `К7` |
| `П без номера` | `П` | початкове ім'я транзитом |

### 6.3. ConstantNameStrategy

Повернути рівно `prefix` правила. Початкове ім'я, номер, маркери та коми не впливають на результат.

Поточні сталі результати:

| Тип/тригер | Результат |
|---|---|
| Опалення `Т11` або `Т21` | `ОПАЛЕННЯ ВОДЯНЕ` |
| Опалення `ЕК` | `ОПАЛЕННЯ ЕЛЕКТРОКОНВЕКТОРНЕ` |
| Каналізація `К1` | `К1` |

### 6.4. TransitNameStrategy

Повернути нормалізовану початкову назву без змін. Застосовується, коли:

- системне ім'я не має правила;
- тип системи не присутній у `system types`;
- динамічне правило не знайшло номер;
- обладнання не знайшло відповідного правила;
- спрацювала захисна перевірка неоднозначної системи.

### 6.5. ClearNameStrategy

Повернути порожній рядок. Використовується, якщо вихідне системне ім'я порожнє. У цьому випадку цільовий параметр має бути очищений.

Правила пошуку:

- Розділити початкову назву за комами та обрізати пробіли у кожній частині.
- Для кожного правила шукати першу частину, що містить будь-який `search` термін.
- Для короткого терміна довжиною до 2 символів вимагати межі токена: поруч не можуть стояти кириличні або латинські літери.
- Для довшого терміна достатній case-insensitive підрядок.
- Якщо будь-який `exclude` є в будь-якій частині назви, правило пропустити цілком.
- Номер витягати лише із знайденої частини, а не з усієї системної назви.

### 8.1. Захист від неоднозначного обладнання

Перед пошуком правил виконати дві перевірки:

1. Якщо в різних частинах назви одночасно знайдено маркер `П + цифри` і `В + цифри`, не застосовувати правило. Повернути всю нормалізовану початкову назву транзитом.
2. Якщо назва містить більше однієї частини й будь-який із маркерів `ПВ`, `ПП`, `П`, `В` трапляється у цих частинах, вважати комбінацію неоднозначною, не перетворювати назву та повернути її транзитом.

Статус такої операції має бути `Transit` з текстом причини у журналі; це не є аварійним завершенням Revit-транзакції.

## 9. Сортування

Сортування не змінює `ADSK_Система_Имя`.

1. Очистити з початку цільового значення всі `U+200B`, `U+200C`, `U+200D`, `U+FEFF` та інші Unicode `Cf`.
2. Якщо значення порожнє, повернути порожній ключ сортування.
3. Визначити префікс у такому пріоритеті:
   - `sort_prefix` правила обладнання;
   - префікс за `system_type_key`;
   - найдовший відомий префікс, з якого починається ім'я.
4. Побудувати ранги з `sort_system_order`. Однакові сусідні префікси утворюють одну групу рангу.
5. Додати до видимого значення `N` символів `U+FEFF`, де `N = rank + 1`.
6. Якщо префікса немає в порядку, використати ранг після останньої групи.

У UI показувати видиме значення без керівних символів і, окремо, рангову групу. У журналі керівні символи мають відображатися безпечно: наприклад, як `U+FEFF × N`.

## 10. Dynamic Updater

### 10.1. Реєстрація

Створити стабільний `UpdaterId`: AddInId застосунку + один незмінний GUID апдейтера. Реєструвати updater як optional.

Реєструвати тригери:

| Фільтр категорій | Trigger Revit | Призначення |
|---|---|---|
| Усі цільові MEP-категорії | `GetChangeTypeElementAddition()` | Синхронізація нового елемента. |
| Усі цільові MEP-категорії | `GetChangeTypeParameter(RBS_SYSTEM_NAME_PARAM)` | Система/ім'я системи змінені. |
| Усі цільові MEP-категорії | `GetChangeTypeParameter(RBS_DUCT_SYSTEM_TYPE_PARAM)` | Змінено тип системи повітроводів. |
| Усі цільові MEP-категорії | `GetChangeTypeParameter(RBS_PIPING_SYSTEM_TYPE_PARAM)` | Змінено тип системи труб. |
| Лише `OST_MechanicalEquipment` | `GetChangeTypeAny()` | Будь-яка зміна обладнання. |
| `OST_DuctSystem`, `OST_PipingSystem` | `GetChangeTypeAny()` | Перерахувати елементи після зміни системи. |
| `OST_DuctSystem`, `OST_PipingSystem` | `GetChangeTypeElementDeletion()` | Очистити застарілі значення після видалення системи. |

Не додавати широкого `GetChangeTypeAny()` для повітроводів або труб: це змінило б поточну поведінку й могло б створити зайве навантаження.

### 10.2. Умови раннього виходу

`Execute` має завершуватись без змін, якщо:

- документ невалідний;
- стан апдейтера для цього документа вимкнений;
- Revit не надав доданих, змінених або видалених IDs;
- конфігурація невалідна;
- цільовий параметр не знайдений.

В `IUpdater.Execute` заборонено відкривати діалоги, показувати pyRevit/output-консоль або кидати необроблений виняток. Помилки треба записувати у файловий журнал і не зупиняти Revit-сесію.

### 10.3. Розширення набору елементів

Початкові IDs — `GetAddedElementIds()` + `GetModifiedElementIds()`.

Для кожного ID:

1. Якщо це ізоляція або облицювання — додати host-елемент. Якщо host недоступний, знайти всі елементи цільових категорій з таким самим `RBS_SYSTEM_NAME_PARAM`.
2. Якщо це труба, повітровід або `MEPSystem` — додати підключене обладнання.
3. Для труби, повітроводу або `MEPSystem` взяти системне ім'я (`MEPSystem.Name` для самого `MEPSystem`) і додати всі цільові елементи з тим самим `RBS_SYSTEM_NAME_PARAM`.
4. Для кожного отриманого неізоляційного елемента додати його ізоляцію й облицювання через Revit API.
5. Не обробляти `MEPSystem` як цільовий елемент; він є джерелом сигналу для розширення набору.
6. Не обробляти вкладені компоненти як кореневі, крім ізоляції/облицювання.
7. Обробити кожен ElementId не більш як один раз за одну подію.

### 10.4. Видалення системи

Якщо є лише `deletedIds`, без доданих або змінених IDs:

1. Просканувати цільові категорії.
2. Відібрати елементи, де `RBS_SYSTEM_NAME_PARAM` порожній, але `ADSK_Система_Имя` ще непорожній.
3. Передати їх у звичайний процесор.
4. Результат `ClearNameStrategy` очистить цільовий параметр.

## 11. Ручний запуск

Команда має:

1. Перевірити, що активний документ — проєкт, не family document і не read-only.
2. Завантажити й перевірити конфігурацію.
3. Зібрати цільові елементи, пропускаючи вкладені компоненти, які не є ізоляцією/облицюванням.
4. Обробити їх у `TransactionGroup` / `Transaction`.
5. Показати підсумок: оброблено, змінено імен, змінено ключів сортування, пропущено, транзитних результатів, помилок, тривалість.
6. Підтримати Escape/cancellation між елементами, завершуючи поточну транзакцію консистентно.

## 12. Запис значень, аудит і журнал

Для кожного елемента:

1. Розрахувати цільове ім'я й, за потреби, ключ сортування.
2. Прочитати поточні значення цільових параметрів.
3. Порівнювати `null` як порожній рядок.
4. Викликати `Parameter.Set()` лише коли значення дійсно відрізняється.
5. Якщо `audit_mode = true`, виконати всі розрахунки й логування, але не викликати `Set()`.

Для журналу кожного нетривіального результату зберігати:

- ElementId, UniqueId, категорію, сімейство, тип;
- початкове системне ім'я;
- ключ типу системи;
- застосовану стратегію;
- текст правила/причини;
- попереднє та нове ім'я;
- попереднє та нове значення сортування;
- ознаку вкладеного/host-елемента;
- статус: `Updated`, `Transit`, `Cleared`, `Warning`, `Error`.

Виключати сімейства, чиї імена починаються з будь-якого `exclude_family_prefixes`, case-insensitive. У поточній конфігурації: `MC Void`, `MC_ConnectionNode`.

## 13. UI та сценарії користувача

### Головна команда

- Кнопка `MEP Parameter Sync` запускає ручну синхронізацію.
- Кнопка або toggle `MEP Parameter Sync АВТО` вмикає/вимикає Dynamic Updater для активного документа.
- Після відкриття документа й активації виду UI має відобразити фактичний стан: updater зареєстрований + документний прапорець увімкнений.

### Вікно налаштувань

Має містити розділи:

1. Цільовий параметр і параметр сортування.
2. Режим аудиту, журналювання, теми, виключені сімейства.
3. Список універсальних маркерів.
4. Порядок систем для сортування: переміщення вгору/вниз, відновлення default.
5. Таблиця правил типів систем: ключ типу, стратегія, префікс, опис у логах.
6. Таблиця правил обладнання: `search`, `exclude`, `prefix`, `sort_prefix`, стратегія, ключ типу, опис.
7. Імпорт, експорт, валідація та збереження JSON.

Перед збереженням показувати всі помилки конфігурації одним списком. Приклад: порожній `search`, невідома стратегія, порожній `prefix` у dynamic/constant правилі, порожній `log`, невідповідна `config_version`.

## 14. Нефункціональні вимоги

- Не виконувати Revit API виклики з фонових потоків.
- Кешувати SystemType name та пошук параметрів у межах одного запуску/updater event.
- У Dynamic Updater не показувати модальних вікон.
- Обробка помилки одного елемента не повинна зупиняти інші елементи події.
- Поведінка має бути детермінованою: однакові вхідні дані -> однаковий результат.
- Використовувати `InvariantCulture` для логіки, яка не повинна залежати від локалі; порівняння маркерів виконувати `OrdinalIgnoreCase`.
- Коректно обробляти кирилицю, латиницю та схожі за виглядом символи без їх автоматичної заміни.

## 15. Критерії приймання

### Функціональна сумісність

- Для всіх 36 правил типів систем результат збігається з Python-версією.
- Для всіх 15 правил обладнання результат збігається з Python-версією.
- Перше відповідне правило обладнання перемагає; виключення мають вищий пріоритет за `search` в межах правила.
- Невідомий тип, невідоме обладнання або відсутній номер не спричиняють помилку: початкова назва зберігається транзитом.
- Порожня система очищає `ADSK_Система_Имя`.
- Ізоляція й облицювання отримують ім'я за host-елементом.
- `audit_mode` не виконує жодного `Parameter.Set()`.

### Dynamic Updater

- Додавання цільового елемента оновлює його параметри.
- Зміна імені системи або типу системи оновлює елемент і пов'язані елементи системи.
- Будь-яка зміна Mechanical Equipment запускає перерахунок.
- Зміна або видалення `DuctSystem`/`PipingSystem` оновлює або очищає пов'язані елементи.
- Видалення системи очищає застарілий `ADSK_Система_Имя` на елементах без системного імені.
- Вимкнений апдейтер не вносить змін.

### Сортування

- Візуальна частина `Unicode Сортування` дорівнює імені системи.
- Префікс із `U+FEFF` має відповідати групі `sort_system_order`.
- Повторний запуск не нарощує приховані символи: старі керівні префікси спершу видаляються.

### Мінімальний набір автоматизованих тестів

- Unit-тести `MepNamingService` для кожної стратегії, кожного типу системи й правила обладнання.
- Unit-тести для маркерів, ком, крапок, суфіксів, Unicode `Cf`, латинських/кириличних варіантів.
- Unit-тести для неоднозначних `П + В` і суміші маркерів.
- Unit-тести `SortNameService` для відомого й невідомого префіксу, однакових сусідніх префіксів і повторного запуску.
- Інтеграційні тести на тестовому RVT: додавання, зміна системного параметра, зміна типу, зміна обладнання, видалення системи, ізоляція та облицювання.
