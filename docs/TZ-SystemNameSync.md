# ТЗ: автозаполнение параметра по «Имени системы» и параметра сортировки (рабочее название **SystemNameSync**)

Версия **v0.2** (после круга 2 уточнений). Статус: черновик для доработки; открытые вопросы — в разделе 17.
Плагин **для Revit на C#**, новая панель во вкладке **HVAC Stuff** (общая надстройка; интеграция — в той сессии/репозитории,
где лежат исходники HVAC Stuff: стили окон, лента, логирование берём оттуда).

> **Принципиальное требование владельца:** писать с нуля, всё изучать и проверять, **не копировать** старый плагин на pyRevit.
> Поведение, о котором владелец знает из старого плагина (ловится потеря и получение системы элементами), используется только как
> ориентир «так должно работать»; реализацию придумываем и проверяем тестами заново.

## 1. Цель
Из системного параметра **«Имя системы»** элемента автоматически (и вручную по кнопке) получать значение и записывать его в
**целевой параметр**; опционально копировать его же с «скрытым префиксом» в **параметр сортировки**, чтобы спецификации шли в нужном
порядке систем. Один порядок систем **на весь проект** (спецификация общая для воздуховодов и трубопроводов).

## 2. Среда
Версии Revit и .NET — как у остальной надстройки HVAC Stuff (на сайте заявлено Revit 2023–2027; уточнить в той сессии).
Язык интерфейса: русский, украинский, английский (как у надстройки). Работает в проекте и в шаблоне проекта (`.rte`).
Рабочие наборы (worksharing) владелец сам не использует, но плагин **должен корректно с ними работать** (раздел 12).

## 3. Лента (панель «название плагина» во вкладке HVAC Stuff)
1. **Кнопка ручного запуска** — полный пересчёт по проекту, в конце отчёт (раздел 11).
2. **Кнопка-переключатель автоматической работы** — вкл/выкл. **Значок показывает реальное состояние** (включено/выключено/не настроено).
3. **Кнопка настроек** — окно настроек (раздел 4).
Состояние переключателя на ленте и переключатель в окне настроек **синхронизированы** (одно состояние, хранится в файле, раздел 7).
При загрузке проекта состояние **восстанавливается из файла проекта** (включён/выключен), **без автоматического пересчёта**.
Если проект не настроен — переключатель неактивен (серый), подсказка «Откройте настройки», **без пугающих сообщений**.

## 4. Окно настроек
Современный интерфейс в стиле HVAC Stuff, окна без системной рамки, перетаскиваемые, числовые/текстовые поля защищены от неверного ввода.

**4.1. Параметры**
- **Целевой параметр** — выпадающий список. Показываются **только подходящие**: текстовые (`Text`), **параметры экземпляра**, привязанные
  **ко всем** категориям из раздела 5 (иначе параметр не в списке). Не только общие: любые подходящие проектные/общие.
- **Параметр сортировки** — такой же список и те же требования.
- Флаг **«Заполнять параметр сортировки»**. Выключен → выпадающий список параметра сортировки **заблокирован**, сортировка нигде не
  заполняется и не контролируется.
- Рядом с плагином лежит **файл общих параметров** (shared parameter file): `ADSK_Система_Имя` (с его GUID) и новый сортировочный параметр
  (имя придумаем, тоже с GUID). Если нужных параметров нет в проекте, плагин **предлагает загрузить/привязать их из этого файла**
  к нужным категориям (по согласию пользователя; детали — открытый вопрос 17.1). Выбрать можно и любой другой подходящий параметр.

**4.2. Постоянный контроль параметров** (на всех этапах: при открытии окна, при запуске, при включении авторежима, в работе апдейтера)
- наличие целевого (и, если включён, сортировочного) параметра в проекте;
- привязка ко **всем** нужным категориям, тип данных «текст», параметр экземпляра, не только для чтения.
- Удаление/изменение параметров во время работы: **отдельный триггер/проверка** (раздел 8.4) — ловим удаление параметра, **отключаем
  апдейтер, показываем понятное сообщение** («параметр … удалён, авторежим выключен, добавьте параметр»). Любая ошибка записи в
  несуществующий/недоступный параметр — то же поведение, без падений.

**4.3. Типы систем и стратегии**
- Разделы **«Типы систем воздуховодов»** и **«Типы систем трубопроводов»**: загружаются **все типы систем проекта**.
- Для каждого типа — **стратегия** из **вшитого списка готовых алгоритмов** (список составим вместе, раздел 9). Стратегия: взять «Имя системы»
  элемента → обработать → записать в целевой параметр.
- **Отдельные настройки стратегий для оборудования** (раздел 9.3).
- **Скрыть тип системы в меню** (системы, которые удалить нельзя, но видеть не хотим): список скрытых хранится в настройках; есть «показать скрытые».
- **Порядок систем для сортировки** — один на весь проект: перетаскиванием **и** кнопками «вверх/вниз»; кнопка **«Загрузить стандартный порядок»**.
- **Пресеты**: сохранить/загрузить всё целиком (стратегии, привязка типов систем к стратегиям, порядок, скрытые типы, выбранные параметры) в
  файл и из файла; **«стоковый» пресет** автора поставляется с плагином и записывается в проект. При загрузке пресета записи для
  несуществующих в проекте типов систем пропускаются без тревожных сообщений.
- **Включение/выключение авторежима** тоже в окне настроек (синхронно с лентой).
- Раздел логирования (раздел 13).

**4.4. Первый запуск без настроек.** Если стоковых типов систем в проекте нет или настроек нет: **никаких угрожающих сообщений**; понятная
подсказка в окне («настройте … , пока не настроено — авторежим не работает»), кнопка «Загрузить стоковые настройки», если они подходят.

## 5. Категории (все MEP)
Арматура воздуховодов, арматура трубопроводов, воздуховоды, трубы, гибкие воздуховоды, (гибкие трубы — уточнить, 17.2), соединительные детали
воздуховодов, соединительные детали трубопроводов, оборудование, воздухораспределители, **материалы изоляции воздуховодов, материалы изоляции
трубопроводов, внутренняя изоляция воздуховодов** (облицовка/Lining). Итоговый список подтвердить (17.2).

## 6. Значение «Имя системы», вложенные семейства, изоляция (требует изучения и проверки в Revit)
- **Простые вложенные семейства** наследуют родителя и отдельно не видны — не обрабатываем.
- **Общие вложенные (shared nested) семейства** в Revit **не получают «Имя системы» от родителя**; значение берём **через родителя**
  (`FamilyInstance.SuperComponent`). Проверить: когда SuperComponent задан, как получить правильное имя (если родитель сам не в системе;
  если родитель подключён к нескольким системам).
- **Изоляция (внешняя и внутренняя)** — у `InsulationLiningBase` есть `HostElementId` (хост: труба/воздуховод/фитинг). Проверить, получает ли
  изоляция «Имя системы» сама; если нет или неверно — брать у хоста. Результат — в таблицу правил (раздел 9).
- Для оборудования — раздел 9.3.
Все эти правила **подтверждаем тестами в реальном Revit** (раздел 15), а не только чтением документации.

## 7. Хранение настроек и состояния
**Прямо в файле проекта/шаблона** — чтобы новый проект из шаблона уже имел настройки и состояние. Предварительно: **Extensible Storage**
(схема с GUID, данные на элементе проекта — `ProjectInfo` или отдельном `DataStorage`; выбрать по результатам проверки, что данные переходят
в новый проект из шаблона, сохраняются при Save As и «Transfer Project Standards» — **проверить**). Версионирование схемы (миграция при
обновлении плагина). Хранится: выбранные параметры, флаг сортировки, стратегии по типам систем, порядок, скрытые типы, состояние авторежима,
настройки логирования (кроме пути), дата/итог последнего полного пересчёта.

## 8. Автоматическая работа (IUpdater)
**8.1. Регистрация.** Апдейтер регистрируется как **необязательный** (`isOptional = true`): тогда проект, который сохраняли с плагином,
открывается на машине без плагина **без большого предупреждающего окна** «updater не найден…» (это окно появляется из-за обязательного
апдейтера; решение: `UpdaterRegistry.RegisterUpdater(updater, document, isOptional)`; **проверить на практике** на трёх сценариях: открыть
файл без плагина после работы апдейтера; при включённом/выключенном авторежиме; при смене флага `SetIsUpdaterOptional`).
**8.2. Реакция.** Авторежим включён → при любом изменении, влияющем на «Имя системы» (элемент получил систему, поменял, **потерял** — в т.ч. удаление
системы клавишей Delete), значение пересчитывается; если системы нет — **целевой и сортировочный параметры очищаются**. Если там уже верное
значение — ничего не пишем (**сравнить и пропустить**).
**8.3. Всю цепочку.** Известная проблема старой версии: цепочка воздуховод–тройник–отвод и ветки обрабатывались **не до конца** (система снималась
не у всех элементов). Требование: при изменении системы обрабатываются **все элементы затронутых систем/ветвей**, до конца.
**8.4. Триггеры — исследовать и выбрать тестами.** Кандидаты (проверить, какие реально срабатывают):
  (а) параметрный триггер на «Имя системы» по категориям;
  (б) «любое изменение» (`GetChangeTypeAny`) по категориям (самый надёжный, но тяжёлый — смотреть по скорости);
  (в) реакция на изменение/удаление **самих элементов систем** (`MechanicalSystem`/`PipingSystem`) → пересчёт элементов этой системы;
  (г) добавление элементов; (д) удаление параметра проекта (раздел 4.2). Выбор — по таблице результатов тестов: что срабатывает, цена в миллисекундах.
**8.5. Оптимизация.** Читать → сравнивать → писать **только при отличии** (проверить измерением, что так быстрее слепой записи); кэш правил стратегий
на прогон; минимум обращений к модели; ранний выход; без лишних транзакций; без бесконечных циклов собственных правок. Бюджет по скорости
определим после первых замеров на реальных проектах (17.6).
**8.6. Повторное включение / выключение / закрытие документа** — аккуратная регистрация и снятие апдейтера.

## 9. Стратегии
**9.1. Общая схема стратегии:** вход — «Имя системы» (и контекст элемента), выход — строка для целевого параметра. Стратегии — вшитый список
(перечисляем с владельцем), выбираются по типу системы. Для каждой — тесты на таблице примеров «вход → выход» (владелец даёт позже).
**9.2. Воздуховоды и трубопроводы.** Таблицы примеров по типам систем — **владелец пришлёт**.
**9.3. Оборудование.** К оборудованию может быть подключено **несколько систем одновременно** (например: `ПВ1 (п)`, `ПВ1 (в)`, `Х3.1`, `Х4.1`, `ДС.1`).
Нужны: (а) как определить, какие системы подключены (коннекторы), (б) правила приоритета «какое имя взять», (в) отдельные настройки стратегий
оборудования. **Владелец опишет типы систем и комбинации**, я предложу варианты стратегий и таблицу приоритетов.

## 10. Сортировка спецификаций
Идея владельца: порядок систем задаётся списком (раздел 4.3); в параметр сортировки записывается **значение целевого параметра с дописанным
скрытым (невидимым) префиксом**, зависящим от позиции системы в списке. Так одна колонка и **показывает имя системы**, и **сортирует**
(у спецификации Revit мало полей сортировки, нельзя тратить на это ещё поле; числовой префикс виден и потому не подходит).
Невидимые символы владелец уже использовал, проблем с сортировкой не было; **какие именно символы** — возьмём из его прежней реализации (по его описанию, не копируя код), проверим сортировку в Revit.
**Исследовать:** есть ли скрытые/малоизвестные возможности Revit API по сортировке спецификации и по увеличению числа полей сортировки (в UI максимум
4 поля «Then by»; в API число полей описано как список — проверить, можно ли через API задать больше 4 и как это отображается; возможно, готовое
решение сообществом). Результат — отдельная заметка; если найдётся лучший способ, обсудим замену невидимого префикса.

## 11. Ручной запуск и отчёт
Полный пересчёт по проекту с прогрессом. **Отчёт** (окно в общем стиле, с возможностью копировать): обработано элементов; записано целевых;
записано сортировочных; **пропущено, потому что значение уже верное**; пропущено, потому что **элемент занят другим пользователем** (список);
элементы без системы (очищены); ошибки (список с причинами); время. Ссылки на элементы по id — клик **только выделяет** элемент.

## 12. Рабочие наборы и хранилища
Если элемент занят другим пользователем — **не правим**, не падаем; ручной запуск — в отчёте список таких элементов и причина; в авторежиме —
краткое сообщение по итогам (без шквала окон): «не обновлено N элементов (заняты), причина …». Проверка — `WorksharingUtils.GetCheckoutStatus`/
попытка записи с обработкой отказа (выбрать по тестам). Журнал фиксирует каждый такой случай.

## 13. Журнал
- Для ручного и авторежима, с возможностью **отключить**. Уровни (минимум: инфо, предупреждения, ошибки; подробный режим — опция).
- Файлы **по датам** и **по размеру** (по умолчанию ~**2 МБ** на файл, автоудаление старше **7 дней**; оба значения — настраиваемые опции).
- Не тормозить: буферизованная запись (не по строке на обращение к диску), без записи в горячем пути авторежима, когда журнал выключен.
- Расположение: **в отдельной папке для этого плагина** рядом с данными надстройки HVAC Stuff (в какой именно — по структуре существующей надстройки, 17.5).

## 14. Нефункциональные требования
Откат одним Ctrl+Z; без заметных тормозов в больших проектах; без пугающих сообщений при первом запуске и при открытии файла без плагина;
русский/украинский/английский интерфейс; ошибки — понятные сообщения со ссылками на элементы и кнопками «Копировать»/«Открыть журнал»
(как в остальных окнах HVAC Stuff); безопасно при удалённых/пропавших параметрах.

## 15. Тестирование (План проверок в живом Revit)
Владелец подключит ко мне **Revit через MCP-сервер**; тесты и тестовые файлы готовлю я (параллельно — юнит-тесты логики стратегий без Revit).
Матрица (минимум): элемент получил/потерял/сменил систему; **удаление системы клавишей Delete**; **длинная цепочка** (воздуховод–тройник–отвод,
ветки) — система снята у **всех** элементов; оборудование с несколькими системами; общие вложенные семейства; изоляция (внешняя, внутренняя) на
трубе/воздуховоде/фитинге; гибкие воздуховоды; изменение типа системы; Undo/Redo; удаление целевого/сортировочного параметра; параметр без привязки
к одной из категорий; элемент в чужом рабочем наборе; открытие файла без плагина (нет окна про апдейтер); создание проекта из шаблона с настройками;
скорость на большом проекте (замеры «сравнить и пропустить» против слепой записи); сортировка спецификации с невидимым префиксом.

## 16. Итоги исследования (по документации, источники ниже; всё, что помечено «проверить», обязательно подтверждаем в Revit)
- **Окно «updater не найден»:** по умолчанию апдейтеры **обязательные**, и документ, изменённый обязательным апдейтером, при открытии без него вызывает
  предупреждающий диалог; есть перегрузка `RegisterUpdater(updater, isOptional)`, для необязательного апдейтера окно не показывается (подтверждено ответом
  на форуме, не официальной документацией; `SetIsUpdaterOptional` — поведение неоднозначно). Источники: [Exposure to End-User (Autodesk Help)](https://help.autodesk.com/cloudhelp/2018/CHT/Revit-API/files/GUID-EEE24659-C2D4-4925-B756-D15A3696D0F8.htm), [Storing Updaters data between Revit sessions (форум)](https://forums.autodesk.com/t5/revit-api-forum/storing-updaters-data-between-revit-sessions/td-p/13437219), [How to Unregister Updater? (форум)](https://forums.autodesk.com/t5/revit-api-forum/how-to-unregister-updater/m-p/8330435).
- **Триггеры:** в одном обсуждении параметрный триггер на системный параметр трубы не срабатывал, а «любое изменение» срабатывало — это подтверждает необходимость выбора
  триггеров тестами; для текстовых параметров экземпляра триггер может требовать, чтобы в области изменения был и тип. Источники: [IUpdater doesn't trigger (форум)](https://forums.autodesk.com/t5/revit-api-forum/iupdater-doesn-t-trigger/m-p/11231347), [IUpdater Trigger based on parameter change (форум)](https://forums.autodesk.com/t5/revit-api-forum/iupdater-trigger-based-on-parameter-change/m-p/4965676/highlight/true), [Registering Updaters (Autodesk Help)](https://help.autodesk.com/cloudhelp/2018/CHT/Revit-API/files/GUID-82B29219-4145-40B1-B713-A439CE1C4829.htm).
