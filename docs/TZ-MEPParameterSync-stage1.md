# ТЗ этап 1: каркас плагина «MEP Parameter Sync» (Revit, C#)

> Самодостаточный текст для передачи в другую сессию (не зависит от остальных файлов репозитория).
> Полное ТЗ проекта — `docs/TZ-MEPParameterSync.md` (используется со 2-го этапа).

## 1. Контекст
Плагин для Revit (MEP) входит в уже существующую надстройку **HVAC Stuff** (вкладка на ленте, общие стили окон, логирование).
Итоговая цель плагина (не для этого этапа): автоматически или вручную заполнять текстовый параметр экземпляра значением,
вычисленным из системного параметра «Имя системы» (`RBS_SYSTEM_NAME_PARAM`), и, по желанию, второй параметр — ключ сортировки
для спецификаций. Работает в ручном режиме (полный пересчёт + отчёт) и в автоматическом (IUpdater).

**Цель этапа 1:** рабочий **каркас**: кнопка на ленте, главное окно с настройками и частично реальным функционалом,
остальное — **заглушки**, на которые потом нарастает логика. Расчёта имён и записи параметров на этом этапе **нет**.

## 2. Что делаем в этапе 1
### 2.1. Реально работает
1. **Лента:** одна кнопка плагина на вкладке HVAC Stuff. Значок показывает **состояние**: авто включено / выключено / не настроено
   (динамическая смена значка).
2. **Главное окно** (по клику; стиль HVAC Stuff: без системной рамки, перетаскивается, Esc закрывает, поля защищены от неверного ввода):
   - переключатель **«Авторежим»** (синхронен со значком на ленте), кнопки **«Пересчитать»** и **«Настройки»**, строка статуса;
   - **Настройки** (разделы-вкладки):
     1. **Параметры.** Два выпадающих списка: **целевой параметр** и **параметр сортировки**. В списках **только подходящие** параметры:
        тип данных «текст», **параметр экземпляра**, не только для чтения, **привязанный ко всем** 14 категориям из п. 3. Флаг
        **«Заполнять параметр сортировки»**: выключен → список сортировки заблокирован. Рядом индикатор проверки («ок» / что не так:
        параметр не найден, не привязан к категории X, не текстовый). Значения по умолчанию для автопредложения: целевой —
        shared-параметр `ADSK_Система_Имя` (GUID `24c33696-0fa2-4a85-affd-e47d1cf20fb3`), сортировочный — параметр проекта
        «Unicode Сортування»; если такого нет — выбор пустой, без ошибок.
     2. **Типы систем.** Два раздела: «Воздуховоды» и «Трубопроводы» — таблицы **реальных типов систем проекта** (`MechanicalSystemType`,
        `PipingSystemType`): имя типа, колонка «Стратегия» (**заглушка**: выпадающий список с пунктами-заглушками), колонка «Скрыт»
        (галочка: скрытые типы не показываются в списках, есть «показать скрытые»).
     3. **Порядок сортировки.** Один список типов систем на весь проект; **перетаскивание мышью и кнопки вверх/вниз**; кнопка
        «Сбросить»; порядок сохраняется.
     4. **Оборудование.** Таблица правил — **заглушка** (пустая таблица с колонками: поиск, исключения, префикс, стратегия; кнопки
        «Добавить/Удалить» работают на уровне UI, без логики).
     5. **Журнал.** Переключатель вкл/выкл, размер файла, срок хранения (дни), кнопка «Открыть папку».
     6. **Импорт/экспорт.** Сохранить/загрузить все настройки в JSON-файл (UTF-8).
   - Кнопки «Сохранить» / «Отмена»; перед сохранением проверка всех настроек и **список всех ошибок одним окном**.
3. **Хранение в самом файле проекта/шаблона:** настройки (JSON-строка) и состояние авторежима записываются через **Extensible Storage**
   (схема с собственным GUID и версией схемы). При открытии проекта настройки и состояние **восстанавливаются**; новый проект из
   шаблона, в котором они были записаны, их получает. Проверить: сохранение/закрытие/открытие, Save As, создание из шаблона.
4. **Журнал:** простая рабочая реализация — файл на каждую дату, разбиение при превышении размера, автоудаление старше N дней,
   буферизованная запись, можно отключить; имя файлов по имени плагина; отдельная папка рядом с данными HVAC Stuff.
5. **Окна сообщений и ошибок** в общем стиле: метка («Информация / Внимание / Ошибка»), заголовок, пояснение, кнопка «Копировать»,
   «Открыть журнал»; если в сообщении есть Id элементов — ссылка, **клик только выделяет** элемент в модели.

### 2.2. Заглушки (интерфейс и поток работают, логики нет)
- **Кнопка «Пересчитать»:** собирает элементы 14 категорий (фильтр по категориям), считает их количество, показывает **окно отчёта**
  (структура будущего отчёта: обработано, записано целевых/сортировочных, пропущено, занято другим пользователем, ошибки, время;
  пока «записано» = 0, видно найденное количество). Esc отменяет. **Параметры не пишутся.**
- **IUpdater:** класс создан и **зарегистрирован как необязательный** (`isOptional = true`) на документ при включении авторежима,
  снимается при выключении/закрытии; `Execute` ничего не меняет, только пишет в журнал, сколько элементов пришло и по какому
  триггеру. Набор триггеров — по умолчанию: добавление элементов и изменение параметра «Имя системы» в 14 категориях +
  изменение/удаление систем (`OST_DuctSystem`, `OST_PipingSystem`). Цель — проверить цепочку «включил → зарегистрировано →
  срабатывает → журнал» и что файл, сохранённый с плагином, **открывается без плагина без большого предупреждения** про апдейтер.
- **Тестер правил** (вкладка/диалог): поле ввода + кнопка, результат — заглушка («Не реализовано»).
- **Стратегии, правила оборудования, расчёт имени и ключа сортировки:** интерфейсы и пустые реализации (`NotImplemented` →
  понятное сообщение «Будет в следующем этапе»).

### 2.3. Не входит в этап 1
Вычисление имён и ключей, запись значений в параметры, реальные стратегии, вложенные семейства/изоляция, рабочие наборы,
оптимизация под большие проекты, полный набор триггеров, пресеты.

## 3. Категории (14), с которыми работает плагин
`OST_DuctAccessory`, `OST_DuctCurves`, `OST_DuctFitting`, `OST_DuctInsulations`, `OST_DuctLinings`, `OST_DuctTerminal`,
`OST_FlexDuctCurves`, `OST_PlaceHolderDucts`, `OST_PipeFitting`, `OST_PipeAccessory`, `OST_FlexPipeCurves`, `OST_PipeCurves`,
`OST_PipeInsulations`, `OST_MechanicalEquipment`.

## 4. Технические требования
- **Интеграция:** сначала изучить исходники HVAC Stuff (лента, сборка, стили окон, логирование, локализация) и **встроиться в них**,
  а не делать отдельную надстройку; версии Revit и целевой .NET — как у HVAC Stuff.
- **Слои (проекты/папки):** `Core` (чистая логика без Revit API: модели настроек, валидатор, журнал-сервис, интерфейсы стратегий,
  отчёт), `Revit` (чтение параметров/типов систем, Extensible Storage, регистрация апдейтера, сбор элементов), `UI` (WPF, окна,
  модели представления), `Addin` (команды, лента), `Tests` (юнит-тесты `Core`). `Core` тестируется без Revit.
- Revit API — только из основного потока. Любая ошибка перехватывается и показывается понятным окном/журналом; **никаких падений
  Revit**; в `IUpdater.Execute` — **без диалогов**.
- **Локализация:** все тексты в ресурсах (ключи), русский / украинский / английский — как в HVAC Stuff.
- **Стиль окон:** общий стиль HVAC Stuff (тёмно-синяя шапка, светлый фон, янтарный акцент, шрифт Segoe UI), без системной рамки,
  перетаскивание, Enter/Esc, кнопка «×» в текстовых полях, числовые поля принимают только числа.
- **Настройки:** модель настроек версионируется (`config_version`), JSON — UTF-8, формат расширяемый (для будущих правил
  типов систем и оборудования заложить секции `settings`, `system types`, `equipment`).
- Код комментируется по-русски; заглушки помечены `// TODO этап N:` с кратким описанием будущей логики.

## 5. Критерии приёмки этапа 1
1. Плагин собирается, кнопка видна на ленте HVAC Stuff, значок меняется с состоянием.
2. Окно открывается, перетаскивается, закрывается Esc; в нём есть все разделы из п. 2.1.
3. Выпадающие списки параметров показывают **только подходящие** параметры (проверить на проекте, где есть параметр, привязанный не
   ко всем категориям: он **не** должен попасть в список).
4. Индикатор проверки показывает причину, если параметр не подходит/не найден; при отсутствии параметров по умолчанию окно
   открывается **без ошибок и пугающих сообщений**.
5. Типы систем проекта загружаются в оба раздела; скрытые типы пропадают из списков; порядок меняется мышью и кнопками.
6. Настройки и состояние авторежима **сохраняются в файле проекта** и восстанавливаются после закрытия/открытия; из шаблона
   новый проект получает их.
7. Экспорт/импорт JSON работает; кривой файл → список ошибок, без падения.
8. «Пересчитать» показывает отчёт с количеством найденных элементов и **ничего не записывает** в параметры.
9. Включение авторежима регистрирует апдейтер; изменение «Имени системы» у элемента даёт строку в журнале; удаление системы
   клавишей Delete — тоже (или явно записано, что не сработало); выключение снимает апдейтер.
10. Проект, сохранённый при включённом апдейтере, **открывается на машине/в сессии без плагина без окна** про апдейтер.
11. Журнал: файл по дате, ротация по размеру и сроку, выключается.
12. Юнит-тесты `Core` зелёные (валидатор настроек, сериализация JSON, журнал-сервис).

## 6. Порядок работы для разработчика
1. Изучить структуру HVAC Stuff, предложить план каркаса (кратко) и согласовать с владельцем: как реализуем кнопку
   (одна кнопка с «панелью управления» или SplitButton), где лежат журналы.
2. Каркас: решение, лента, пустое окно, хранилище настроек (Extensible Storage), журнал.
3. Вкладки настроек по очереди (параметры → типы систем → порядок → журнал → импорт/экспорт).
4. Заглушки пересчёта и апдейтера, отчёт, окна сообщений.
5. Тесты `Core`; сводка того, что **не проверено в живом Revit** и как это проверить владельцу.
Всё, что нельзя проверить без Revit, честно помечать как «не проверено».
