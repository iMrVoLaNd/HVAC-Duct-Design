# ТЗ: MEP Parameter Sync — автозаполнение параметра по «Имени системы» и ключа сортировки (C#, Revit)

Версия **v0.3.1** (после круга 3 и получения актуального `settings.json`). Статус: черновик, почти готов к передаче в разработку; открытые вопросы — раздел 18.
Плагин входит в общую надстройку **HVAC Stuff** (новая панель/кнопка на её вкладке; стили окон, ленту и логирование берём из исходников HVAC Stuff в той
сессии/репозитории, где они лежат).

**Документы:**
- этот файл — актуальное ТЗ: что строим и чем отличается от прежней реализации;
- **[`docs/stock/MEPParameterSync.settings.json`](stock/MEPParameterSync.settings.json) — «Приложение B»**: **актуальные настройки владельца** (config_version 3): 36 правил типов систем, 15 правил
  оборудования, порядок сортировки, 61 универсальный маркер. Это **стоковый пресет** и **эталон для тестов** (разбор — раздел 7.1).
- **[`docs/MEPParameterSync-legacy-spec.md`](MEPParameterSync-legacy-spec.md) — «Приложение A»**: спецификация прежней Python-реализации (matrix из 36 правил типов систем,
  15 правил оборудования, алгоритм имени, алгоритм сортировки, триггеры апдейтера). Это **основа и база совместимости**: на стоковых настройках результат
  C# должен совпасть с прежним. Ссылки вида «A §7» — на разделы этого приложения.

> **Принцип владельца:** писать **с нуля**, всё изучать и проверять; прежняя реализация — источник правил и ориентир «как должно быть», но новая версия
> строится на её основе с **новыми, более современными стратегиями** (раздел 9). Расхождения с прежним поведением — только осознанные и записанные здесь.

## 1. Цель
Из системного параметра **«Имя системы»** (`RBS_SYSTEM_NAME_PARAM`) получать итоговое имя и записывать его в параметр **ADSK_Система_Имя**
(shared, GUID `24c33696-0fa2-4a85-affd-e47d1cf20fb3`); опционально формировать **ключ сортировки** в параметре проекта **«Unicode Сортування»**
(видимое имя + скрытый префикс `U+FEFF × (ранг+1)`, A §9), чтобы спецификации шли в заданном порядке систем (один порядок **на весь проект**).
Два режима: ручной (полный пересчёт + отчёт) и автоматический (IUpdater).

## 2. Среда и сборка
- Версии Revit и целевой .NET — **как у остальной надстройки HVAC Stuff** (на сайте: Revit 2023–2027 ⇒ вероятно мультитаргет: .NET Framework 4.8 для ≤2024,
  .NET 8 для 2025+; уточнить в сессии надстройки). Учесть `ElementId` = `long` с Revit 2024.
- Языки интерфейса: русский, украинский, английский (как у надстройки). Имена типов систем и правил — украинские (ADSK_…_Приплив и т.п.), хранятся как есть.
- Проект и шаблон проекта (`.rte`); family-документы не поддерживаются.
- Рабочие наборы (worksharing) владелец не использует, но поддержка обязательна (раздел 13).

## 3. Лента
**Одна кнопка** плагина на вкладке HVAC Stuff (решение владельца: не плодить кнопки). Реализация — **на выбор владельца (вопрос 18.1)**:
- **(рекомендую) «Панель управления»**: клик открывает компактное окно с тремя действиями: **переключатель «Авторежим»** (вкл/выкл), кнопка **«Пересчитать всё»**
  (ручной полный запуск), кнопка **«Настройки»**; в окне — статус (включено/выключено/не настроено, дата и итог последнего пересчёта);
- вариант SplitButton: главная часть — переключатель авторежима (значок меняется), в выпадающем списке — «Пересчитать» и «Настройки».
**Значок кнопки на ленте всегда показывает реальное состояние** (включено / выключено / не настроено) и синхронизируется с переключателем в окне настроек.
При загрузке проекта состояние **восстанавливается из файла проекта** (без автоматического пересчёта).

## 4. Окно настроек
Современный интерфейс в стиле HVAC Stuff; окна без системной рамки, перетаскиваются; ввод защищён от неверных данных; «Копировать» и ссылки на элементы в сообщениях.

**4.1. Параметры.** Выпадающие списки показывают **только подходящие** параметры: текстовые, **экземпляра**, привязанные **ко всем** категориям раздела 5, не только для чтения.
- **Целевой** — по умолчанию `ADSK_Система_Имя` (shared, ищется по GUID; если в проекте его нет — диагностика, см. 4.2).
- **Параметр сортировки** — по умолчанию проектный параметр `Unicode Сортування` (ищется по имени/ключу). Флаг **«Заполнять параметр сортировки»**: выключен → список параметра заблокирован, сортировка нигде не заполняется и не контролируется.
- Параметры может выбрать и любые другие подходящие.
- **Создавать недостающие параметры автоматически не будем** (как в прежней версии, A §2): только диагностика с понятной инструкцией (какой параметр, какие категории) и, при желании, подсказка загрузить из общего файла параметров. Помощник привязки — возможная вторая очередь (18.4).

**4.2. Постоянный контроль параметров** — при открытии окна, при запуске, при включении авторежима, в работе апдейтера (дешёвая проверка «параметр существует» при каждом срабатывании):
- есть ли целевой (и, если включён, сортировочный) параметр; привязка ко всем категориям; тип «текст»; параметр экземпляра; не read-only.
- **Параметр удалили/отвязали** — отдельный триггер/проверка (раздел 8.4): авторежим **выключается**, понятное сообщение («параметр … удалён, авторежим выключен…»), без падений.

**4.3. Правила**
- **Типы систем** (воздуховоды, трубопроводы — два раздела): подгружаются **все типы систем проекта** (точные имена). Для каждого — стратегия (раздел 9) с параметрами.
- **Оборудование** — отдельная таблица правил (раздел 9.3).
- **Скрытие типов систем в меню** (системы, которые нельзя удалить, но не нужны): список скрытых в настройках, «показать скрытые».
- **Порядок систем для сортировки** — один на весь проект: перетаскиванием и кнопками вверх/вниз; «Загрузить стандартный порядок».
- **Универсальные маркеры**, **исключаемые сімейства** (по префиксу, A §5.1), **режим аудита**, **логирование**, **тема интерфейса**.
- **Пресеты:** сохранить/загрузить всё в файл (JSON) и из файла; **стоковый пресет** (текущий `settings.json` владельца, config_version 3) поставляется с плагином и применяется кнопкой «Загрузить стоковые настройки».
- **Валидация** перед сохранением: **все ошибки одним списком** (A §13): пустой `search`, неизвестная стратегия, пустой `prefix` у dynamic/constant, пустой `log`, неподходящая версия конфигурации.
- **Тестер правил (новое):** поле «введите имя системы / выберите тип системы» → показывает результат и **почему** (какое правило, какая стратегия, какой токен) — для отладки правил без запуска по проекту.

**4.4. Первый запуск без настроек / без стоковых систем.** Никаких угрожающих сообщений: спокойная подсказка («Пока не настроено. Загрузите стоковые настройки или настройте правила; авторежим не работает, пока не настроено»); кнопки на ленте — в состоянии «не настроено».

## 6. Имя системы, вложенные семейства, изоляция
Правила чтения входных данных — A §4.1: для изоляции и облицовки источником имени и типа является **элемент-хост**; вложенные компоненты как корневые не обрабатываются (кроме изоляции/облицовки).
**Общие вложенные (shared nested)** семейства не наследуют имя системы — берём **через родителя** (`FamilyInstance.SuperComponent`); **проверить в Revit:** когда SuperComponent задан, что при родителе без системы или с несколькими системами.
**Изоляция** — `HostElementId`; проверить, получает ли изоляция имя системы сама (может быть корректно и без хоста); результат фиксируем в таблице правил и тестами (раздел 16).

## 7. Хранение настроек и состояния
**Прямо в файле проекта/шаблона**, чтобы новый проект из шаблона получал всё сразу (решение владельца; в отличие от прежней версии, где настройки лежали в `settings.json` рядом с плагином, а в файле хранился только флаг авто).
Способ: **Extensible Storage** (схема с GUID; настройки как JSON-строка плюс отдельные поля: состояние авто, версия схемы; хранилище — `ProjectInfo` или `DataStorage`, выбрать после проверки, что данные переходят в проект из шаблона, сохраняются при Save As и **Transfer Project Standards** — проверить). Версионирование схемы и миграции.
`settings.json` (JSON, UTF-8) остаётся как **формат обмена** (импорт/экспорт/стоковый пресет), его структура — A §5 (`settings`, `system types`, `equipment`).
**Импорт прежнего формата обязателен:** файл с `config_version: 3` (Приложение B) импортируется без потерь (в т.ч. строка или массив в `search`/`exclude`, пустой `system_type_key`, поля, которые новая версия не использует, — например `ui_theme: theme_angel.xaml` — игнорируются без ошибок). Тест «импорт Приложения B → экспорт → сравнение» — в приёмке.

### 7.1. Что видно в актуальных настройках (Приложение B) — важно для реализации
- Совпадает со старым ТЗ: **36** правил типов систем и **15** правил оборудования; стратегии только `DynamicNameStrategy` и `ConstantNameStrategy`; везде `sort_prefix = prefix`.
- **Маркеры (61):** 24 чисто латинских и **9 «смешанных»** написаний с похожими символами (`ДC`, `TП`, `ПB`, `BП`, `ФB`, `BД`, `XП`, `ТX`, `TХ` — часть букв латиницей). Автозамену «похожих» символов не делаем — **хранить и сравнивать строго как в файле** (`OrdinalIgnoreCase`), в тестах — именно эти варианты. (Возможное улучшение — нормализация гомоглифов вместо ручного списка; обсудить, 18.9.)
- **Порядок сортировки (42)** отличается от `default_sort_system_order` (44): в текущем порядке **нет** `ADSK_17_ТХ_Технологія` и пункта `Прочее`. Для ТХ при такой настройке ключ сортировки получит «ранг после последней группы» (A §9.6) — возможно, это упущение (18.10).
- В порядке есть **7 типов систем без правил именования** (стандартные русские типы Revit: «Вентиляционное отверстие», «Водяная система пожаротушения», «Газовая…», «Горячее водоснабжение», «Дренчерная…», «Другие системы пожаротушения», «Холодное водоснабжение») — их имена идут транзитом, а порядок задан по имени типа.
- Префикс **`ПП`** встречается у двух типов, расположенных в порядке **далеко друг от друга** (`ADSK_07_ПП_Приплив` и `ADSK_19_Підпір повітря_ПП`) — поэтому ранг нельзя определять только по префиксу; нужна точная формулировка (18.10).
- Журнал в старых настройках: каталог `log`, **7 дней**, **8 МБ** на файл, журнал включён, аудит выключен, метрики выключены.
## 8. Автоматическая работа (IUpdater)
**8.1. Регистрация.** Стабильный `UpdaterId` (AddInId + постоянный GUID). Регистрация **необязательным** (`isOptional = true`): проект, сохранённый с плагином, открывается без него **без большого окна «updater не найден»**. Проверить на практике: открытие файла без плагина при включённом/выключенном авто; `SetIsUpdaterOptional`. Регистрация на документ (состояние per-document), снятие при закрытии.
**8.2. Реакция.** Начальный набор триггеров — A §10.1: добавление элемента (`ElementAddition`); параметрные триггеры на `RBS_SYSTEM_NAME_PARAM`, `RBS_DUCT_SYSTEM_TYPE_PARAM`, `RBS_PIPING_SYSTEM_TYPE_PARAM`; для оборудования `GetChangeTypeAny`; для `OST_DuctSystem`/`OST_PipingSystem` — `GetChangeTypeAny` и `ElementDeletion`. **Не** добавлять широкий `GetChangeTypeAny` для воздуховодов/труб. **Обязательно уточняется тестами** (раздел 16): что реально срабатывает, цена в мс; по результатам набор может поменяться.
**8.3. Ранний выход, без диалогов, без исключений наружу** — A §10.2.
**8.4. Расширение набора (вся цепочка).** Цепочка «воздуховод–тройник–отвод» и ветки должны обрабатываться **целиком** (известная проблема прежней версии: обработка останавливалась на части элементов). Базовый алгоритм — A §10.3 (хост для изоляции, подключённое оборудование, все элементы той же системы). **Улучшение (новое, проверить):** вместо поиска по всей модели по строке имени — брать элементы системы из сети (`MechanicalSystem`/`PipingSystem`: сети элементов) и обходить коннекторы; для надёжности при удалении системы — быстрый поиск «осиротевших» (A §10.4) через **параметрные фильтры уровня базы** (целевое значение есть, имени системы нет — `HasValue`/`HasNoValue`), а не полным перебором.
**8.5. Удаление параметра** — отдельный триггер/проверка (4.2).
**8.6. Оптимизация (10 000+ элементов, разные проекты).** Читать → сравнивать → писать **только при отличии** (измерить выигрыш); кэш правил и имён типов на событие; ранний выход; ни одной лишней транзакции; без повторной обработки одного элемента за событие; никаких Revit-вызовов из фоновых потоков. Замеры на крупных проектах — часть приёмки (16).

## 9. Стратегии (на основе прежних + новые)
**9.1. База совместимости (обязательно)** — четыре прежние стратегии и их точный алгоритм из A §6: `DynamicNameStrategy` (префикс + номер; маркеры, токены, запятая, точка, суффикс; нет номера → транзит), `ConstantNameStrategy`, `TransitNameStrategy`, `ClearNameStrategy` (в пользовательских правилах запрещена). 36 правил типов систем (A §7) и 15 правил оборудования (A §8) со всеми исключениями и защитой от неоднозначности (A §8.1) — **стоковая конфигурация, результат совпадает с прежней**.
**9.2. Предложения по новым стратегиям (выбрать, 18.2):**
- **N1. Template** — результат по шаблону с подстановками: `{prefix}{number}{suffix}`, `{type}`, `{raw}` (например, `ОПАЛЕННЯ {number}`); заменяет часть «Constant» без жёсткого кода.
- **N2. Map (таблица соответствий)** — набор «регулярное выражение / маска → результат» внутри одного правила (покрывает случаи вроде Т11/Т21 → «ОПАЛЕННЯ ВОДЯНЕ» одной строкой правила вместо отдельных типов).
- **N3. ByConnectedSystems (для оборудования)** — вместо длинных списков `exclude` и разбора склеенной строки имени: определить **подключённые системы** оборудования (через коннекторы → тип/имя каждой системы) и выбрать **по приоритетной таблице типов систем** («если подключены ПВ и П — берём ПВ»); явная политика конфликтов: «Приоритет / Транзит / Предупреждение».
- **N4. Цепочка запасных вариантов** — стратегия «попробуй A, иначе B, иначе транзит» (убирает множество скрытых зависимостей между правилами).
- **N5. Объяснимость:** у каждого результата код причины/стратегия/правило — в отчёте и журнале; фильтр «что ушло в транзит»; **отчёт «неохваченные имена систем»** (какие реальные имена не подошли ни под одно правило) — помогает достраивать правила.
- Режим **аудита** (dry run): всё считается и логируется, `Set()` не вызывается (A §12).
**9.3. Оборудование.** К одному оборудованию подключено много систем (пример: `ПВ1 (п)`, `ПВ1 (в)`, `Х3.1`, `Х4.1`, `ДС.1`…). Базово — правила A §8 (порядок, `search`/`exclude`, границы токенов, защита «П+В»); в новой версии добавляется N3. Нужны ваши таблицы приоритетов (18.3).

## 10. Сортировка
Алгоритм из A §9 (очистка `Cf`-символов, префикс по приоритету: `sort_prefix` правила оборудования → `system_type_key` → самый длинный известный префикс; ранги из `sort_system_order`, соседние одинаковые префиксы — одна группа; **`U+FEFF` × (ранг+1)**; префикс, которого нет в порядке — ранг после последней группы). Повторный запуск не наращивает скрытые символы. В UI — видимое значение без управляющих символов и ранг отдельно; в журнале — `U+FEFF × N`.
**Исследование (отдельной заметкой):** скрытые/малоизвестные возможности API по сортировке спецификаций и по числу полей сортировки (в UI максимум 4; в API — список; >4 через API не подтверждено).

## 11. Ручной запуск и отчёт
Проверки: проект (не family, не read-only), конфигурация валидна, параметры на месте. Обработка в `TransactionGroup`/`Transaction`, прогресс и отмена (Esc) между элементами с консистентным завершением. **Отчёт** (окно в стиле HVAC Stuff, «Копировать», ссылки на элементы — клик только выделяет): обработано; изменено имён; изменено ключей; пропущено (значение уже верное); **занято другим пользователем** (список и причина); транзитных; очищенных (без системы); ошибок (список, причины); время (и метрики производительности при включённой опции).

## 12. Запись значений, аудит
A §12: рассчитать → прочитать текущее → сравнить (`null` = пустая строка) → `Parameter.Set()` только при отличии → при аудите не писать. Журнал — поля A §12 (ElementId, UniqueId, категория, семейство, тип, исходное имя, ключ типа, стратегия, причина, старое/новое имя и ключ, признак вложенного/хоста, статус `Updated/Transit/Cleared/Warning/Error`). Исключение семейств по префиксам (`MC Void`, `MC_ConnectionNode`).

## 13. Рабочие наборы
Занятый другим пользователем элемент **не правим**, не падаем; ручной запуск — в отчёте список и причина; авто — краткое итоговое сообщение (без потока окон: «не обновлено N элементов — заняты»); журнал фиксирует каждый случай. Способ определения — `WorksharingUtils`/обработка отказа записи (по тестам).

## 14. Журнал
Для ручного и авто режимов, можно **отключить**. Файлы **по датам** и **по размеру** (по умолчанию **8 МБ** (как в прежних настройках; вы называли ~2 МБ — уточнить, 18.11), хранение **7 дней**; обе опции настраиваемые), буферизованная запись (не по строке), без записи на «горячем пути», когда журнал выключен. Имя файлов — **по имени плагина** (например, `MEPParameterSync_YYYY-MM-DD_N.log`); папка — **отдельное место под этот плагин** рядом с данными HVAC Stuff (по структуре надстройки; 18.5). Управляющие символы в журнале — безопасно (`U+FEFF × N`).

## 15. Нефункциональные требования
Откат одним Ctrl+Z; детерминированность; `InvariantCulture`/`OrdinalIgnoreCase` в логике; без автозамены кириллицы/латиницы; без модальных окон в `Execute`; ошибка одного элемента не останавливает остальные; никаких пугающих сообщений при первом запуске/открытии без плагина; все окна — общий стиль HVAC Stuff (тёмная/светлая тема сайта и окон не навязывается системой).

## 16. Тестирование и приёмка
Владелец подключит **Revit через MCP-сервер**; тестовые файлы и сценарии готовит разработчик (Claude). Два слоя:
1. **Юнит-тесты логики без Revit** (`Core`): каждая стратегия, **все 36 + 15 правил** (результат = A §7–8), токены/запятые/точки/суффиксы, Unicode `Cf`, латиница/кириллица, неоднозначные «П+В», `SortNameService` (известный/неизвестный префикс, соседние одинаковые, повторный запуск), валидатор конфигурации, импорт/экспорт.
2. **Интеграционные тесты в Revit:** добавление; смена имени/типа системы; смена оборудования; **удаление системы клавишей Delete**; **длинная цепочка** (воздуховод–тройник–отвод, ветки) — снято у **всех**; оборудование с несколькими системами; общие вложенные семейства; изоляция внешняя/внутренняя на трубе/воздуховоде/фитинге; гибкие; удаление/отвязка целевого и сортировочного параметра; параметр не привязан к одной из категорий; чужой рабочий набор; **открытие файла без плагина — окна про апдейтер нет**; проект из шаблона с настройками; Undo/Redo; сортировка спецификации с `U+FEFF`; **скорость на проектах 10 000+ элементов** (в т.ч. сравнить «читать-сравнивать-писать» и слепую запись).
Критерии приёмки — A §15 плюс пункты выше. Что нельзя проверить без Revit — честно в список «не проверено».
